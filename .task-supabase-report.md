## Implemented boundary

- The SQL migration creates all five required tables, unique indexed public
  tokens, expiration/lifecycle checks, RLS with no direct anonymous table
  privileges, and narrow `SECURITY DEFINER` RPCs.
- Supabase repositories use an RPC transport behind TanStack Start server
  functions. Only request handlers read the two unprefixed environment
  variables and instantiate the Supabase client.
- Recordings, accounts, and recipient runs remain in the local demo store.
  Shared records use Supabase when configured and an explicit in-process
  local-only adapter in development/tests.
- Tokens use 18 random bytes (144 bits), base64url encoded.
- Helper decisions are detected by 2.5-second polling.

## Limitations

- No Supabase credentials were provided, so the migration was not applied and
  no live Supabase or deployed Vercel acceptance run was claimed.
- The local-only adapter proves independent clients sharing one persistence
  transport, but it intentionally does not survive server restarts or work
  across devices.
- Secure anonymous RPCs intentionally do not provide list-all operations.
  Without workspace authentication or a server-only service credential, a
  list-all RPC would let anyone holding the anon key enumerate shared records.
- No `vercel.json` was added because Nitro emits the server output and no static
  rewrite is required.

### Final architecture

- Owner workspace capability generation and reads occur only inside TanStack
  server functions. A Secure, HttpOnly, SameSite=Lax, Path=/ session cookie
  scopes the sender workspace to Browser A; there is no localStorage or
  process-global owner fallback and no owner token in client-visible transport
  inputs.
- Runtime shared resources are Supabase-only. Browser storage is constructed
  only for recordings, demo accounts/runs, and UI state; the in-memory shared
  adapter is selected only by automated tests.
- Handoff policy is preserved and enforced for safe preferences and helper
  escalation in UI/WebMCP and SQL capability operations. Consequential submit
  retains the platform minimum fresh human confirmation even when the handoff
  does not add its own confirmation requirement.
- Public DTOs omit sender note/recipient, database/external IDs,
  `recordingId`, `sourceEventIds`, and procedure step IDs. They retain only
  route execution fields and the policy needed for recipient enforcement.
- Completed/expired parents deny helper reads, decisions, polling, and public
  activity. Expiry is persisted during owner/public handoff reads and
  transitions.
- All recipient human command activity and WebMCP command/audit activity use
  the public handoff capability and attach to the sender-owned handoff.
- SQL uses exact enum/discriminated validators, empty `search_path` on every
  definer function, capability-scoped grants, and advisory-lock-protected
  per-owner quotas: 50 procedures, 100 handoffs, 200 helper requests, and
  2,000 activity events.
